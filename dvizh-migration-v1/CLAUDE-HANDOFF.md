Обновлено: 2026-09-15. Этот файл позволяет продолжить работу без истории ChatGPT.
При расхождении с живым сервером сначала выяснить расхождение, не подгонять файлы.

## Задача владельца

Заканчивается бесплатный период exe.dev. Нужно сохранить ВСЁ рабочее окружение и
данные, перенести на другой сервер максимально простым способом: команды для двух
терминалов, без установки Remote Desktop на компьютер. Владелец обычно работает
с телефона. Далее разработка, вероятно, продолжится через Claude Code.

Приоритет — не новый дизайн или инфраструктурный фреймворк. Цель — не потерять
данные и продолжить использовать планировщик. Новый сервер, ОС, доступ и домен
на момент подготовки этого файла ещё не указаны.

## Известные компоненты (подтвердить по live inventory)

- `/opt/dvizh` — PWA и Python backend; `/var/lib/dvizh` — persistent data.
- Backend хранит JSON-state по user_id в SQLite (WAL) и историю revisions.
  Код для чтения контракта:
  `minimal-ui-v1/health-recovery-v1/baseline/helpers/server.py`.
- `dvizh-auth-release/README.md` описывает **собственный шлюз входа** на
  `127.0.0.1:8002`, backend на `127.0.0.1:8000`.
  Пароль/сессии/стабильную identity надо переносить, не создавать нового пользователя
  и пустую базу вместо старого. `/var/lib/dvizh/auth-identity.json` используют bridges.
- Backend доверяет `X-ExeDev-UserID`/`X-ExeDev-Email`. Шлюз должен удалять подставленные
  клиентом заголовки и выставлять identity только после авторизации. Снаружи нельзя
  открывать backend напрямую. Сохранить существующую auth-логику, не делать обход.
- `/opt/dvizh-ai-home/ai_home_bridge.py`; env ожидается `/etc/dvizh/ai-home.env`.
  Defaults в коде: WEB_API `127.0.0.1:8000`, HERMES_API `127.0.0.1:8642/v1`.
  Есть отдельные HERMES_API_KEY и HERMES_API_MODEL. Значения не выводить в отчёты.
- `hermes-control-v1/systemd/dvizh-ai-home.service` и
  `dvizh-ai-approval.service` — исходные contracts, не доказательство точных live units.
- `/home/exedev/.hermes` — конфигурация, skills, память/сессии, dev worktrees,
  handoffs, очереди и backup. Содержимое не публиковать. Уточнить расположение
  исполняемого Hermes, venv, моделей и user-systemd units.
- `/usr/local/bin`, `/usr/local/sbin`, `/usr/local/libexec`, `/etc/dvizh*`,
  `/etc/systemd/system`, `/var/lib/dvizh*`, cron/timers, Docker volumes и другие
  приложения вне DVIZH тоже проверить. Незнакомые mounts — не игнорировать.
- При наличии `.claude`, `.codex`, `.config`, `.local`, `.ssh`, локальных репозиториев

## Минимальный путь переноса

1. Прочитать короткий live inventory со старого сервера. Получить ОС/архитектуру,
   диск, адрес и разрешённый owner-доступ нового сервера. Уточнить домен/HTTPS.
2. Составить полный список данных, локальных исполняемых программ, служб,
   внешних credentials/integrations, mounts и источников записи. Дополнить inventory
   локально; не выводить секреты/личные заметки в transcript. Сохранить package
   manifest, реальные units/drop-ins, users/groups и метаданные приватно в backup.
3. Создать независимую приватную копию ВНЕ exe.dev до окончания аренды. Передача
   напрямую по подтверждённому SSH-каналу; архив при хранении зашифрован. Ключи
   вводит/создаёт владелец в терминале. Временный доступ ограниченный и отзываемый.
   Никаких публичных HTTP backup URLs, токенов в аргументах/логах или uploads в repo.
4. Первую большую копию можно сделать без переключения. Перед финальным снимком
   временно остановить согласованный полный список writers (приложение, Hermes,
   workers, cron/timers и контейнеры), дождаться завершения транзакций и сделать
   финальную копию/дельту. Не останавливать SSH или системную сеть. Не применять
   rsync --delete к корню целевого сервера.
5. SQLite переносить согласованно, учитывая WAL. Применять SQLite backup API для
   live-снимков отдельных баз, либо копировать остановленный согласованный набор.
   Для общей точки переключения нескольких баз всё равно нужен контроль writers.
   Для PostgreSQL/MySQL — соответствующие dump/restore или штатный physical backup,
   а не tar работающего datadir. У разных DB может быть разный backup contract.
6. На новом сервере проверить пустоту согласованных целевых каталогов и ресурсы.
   Восстановить сначала в root-owned staging: сверить SHA256, список и размер,
   запретить path traversal/небезопасные ссылки. Сохранить владельцев/режимы/ACL/xattrs
   или выполнить проверенное сопоставление пользователей без расширения прав.
7. НЕ заменять новой машине SSH host keys, сеть, netplan, cloud-init, machine-id,
   загрузчик, fstab, passwd/shadow или весь `/etc` старой машины. Хранить исходные
   конфиги в архиве для анализа, активировать только согласованные сервисные части.
   Зависимости/venv проверить на новой ОС/архитектуре; не считать их переносимыми
   только из-за совпадения имён каталогов.
8. Настроить независимый HTTPS-вход перед существующим auth gateway. Домен
   `*.exe.xyz`, proxy и host-side integrations exe.dev — не часть файлового архива.
   При использовании `*.int.exe.xyz` перенастроить доступ через штатный provider,
   не добывать скрытые provider credentials. Смена подписки помощника сама по себе
   не подтверждает работу live API Гермеса на новом сервере.
9. Проверить новый host, затем явно переключить единственного writer/ботов/очереди.
   Старый сохранить выключенным для записи, но доступным для rollback. Не включать
   два Telegram poller или два набора cron/Hermes одновременно.

Перед сменой адреса пользователь должен дождаться sync реальных задач и сохранить
неотправленные черновики. Browser storage принадлежит старому origin и не входит
в server backup. Не очищать browser data ради устранения cache.

## Acceptance и откат

На новом сервере проверить: целостность всех баз, количество записей и revisions
без вывода содержимого, exact static-файлы, identity пользователя, login/logout,
отказ неавторизованному доступу к данным, HTTPS и отсутствие прямого backend-порта.
`GET /api/health` должен вернуть именно JSON `{ok:true, app:"dvizh", ...}`;
HTML с HTTP 200 и несуществующий `/api/ai-home/health` не подходят.

Проверить расписания/часовой пояс, автозапуск после reboot, отсутствие двойных
workers, readonly AI-context, pending proposals и approval boundary, затем голос
и озвучку на Android. Состояниеизменяющие тесты — изолированные fixtures или
отдельно согласованные реальные действия пользователя.

До удаления старого сервера должен существовать проверенный backup вне старого
провайдера, его checksum, реальный путь и проверка восстановления. Конечный отчёт:
что включено/исключено, source/destination, окно финального snapshot, версии,
хеши, статус DB/auth/services, реальный backup, результат пользовательского теста.
Не объявлять `inventory` или успешное скачивание завершённым переездом.

При сбое не удалять старый экземпляр/backup. Если на новом уже были записи, нельзя
просто включить старую базу: согласовать возврат последних данных и единственного
writer. После успешной миграции отозвать временные SSH-доступы.
