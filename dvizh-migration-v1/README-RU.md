# Перенос сервера DVIZH

Статус пакета: **подготовка переноса, не установщик и не резервная копия**.
Рабочие данные в этот репозиторий не входят. На новом сервере пока ничего не установлено.

## Что уже есть

`inventory.py` — проверка состава старого сервера без изменения служб и приложения.
Она показывает ОС, архитектуру, свободное место, объёмы основных каталогов, точки
монтирования, службы, Docker mounts и соответствие пяти клиентских файлов последней
подтверждённой установленной версии.

Скрипт НЕ читает содержимое `.env`, SSH-ключей, пользовательских баз и памяти Гермеса.
Он не вызывает Hermes/Claude, не устанавливает пакеты, не меняет sudoers/firewall,
не останавливает службы и не передаёт отчёт по сети. Единственный HTTP-запрос —
локальный GET `/api/health`; из ответа сохраняется только результат проверки.

По умолчанию вывод короткий. `--json` даёт подробные технические метаданные.
`--output /путь/к/новому-файлу.json` дополнительно создаёт отчёт с правами 0600;
существующий файл не перезаписывается. Отчёт не содержит значений секретов, но
содержит техническую структуру сервера: его не нужно публиковать на открытых сайтах.

## Старый сервер

В owner-сессии `exedev@rikarishi-dvizh`, после проверки SHA256 скачанного файла:

```sh
sudo /usr/bin/python3 -I -S inventory.py
```

Для полного отчёта и передачи следующему разработчику на самом сервере:

```sh
sudo /usr/bin/python3 -I -S inventory.py --json
```

Это НЕ архивирование данных. Наличие успешного отчёта не защищает от окончания
срока аренды сервера. Следующий обязательный этап — независимая резервная копия
на новом сервере или в другом хранилище, недоступном посторонним.

## Как должен выглядеть законченный перенос

Одна команда подготовки на старом сервере и одна команда мастера переноса на новом.
Разрешение соединения между серверами и выбор нового адреса выполняются владельцем.
Автоматизация не должна требовать передачи приватных ключей, паролей или backup
с личными данными в чат или GitHub.

До создания команды восстановления нужно знать:
- результат проверки фактического состава старого сервера;
- ОС и архитектуру нового пустого сервера, доступный диск;
- собственный домен или согласованный новый HTTPS-адрес;
- разрешённый владельцем способ подключения старого и нового серверов.

Сначала копируются данные в закрытую staging-зону, проверяется полнота. Старый
сервер остаётся рабочим до этапа переключения. Перед финальным снимком нужно
приостановить все обнаруженные источники записи, а не только HTTP-сервер: Hermes,
очереди, cron/timers, Telegram и другие workers. После проверки на новом сервере
должен остаться ровно один активный комплект этих служб.

Нельзя накатывать весь старый `/` поверх нового Linux. SSH, сеть, загрузчик,
cloud-init и идентификатор машины нового сервера должны сохраниться. Нельзя
публиковать порт backend 8000 без существующего шлюза авторизации.

Полный порядок, текущая версия и нерешённые вопросы — в `CLAUDE-HANDOFF.md`.

## Локальные проверки пакета

```sh
python3 -m unittest discover -s tests -v
```

Проверки используют фикстуры и поддельные ответы служебных команд. Они НЕ являются
проверкой переноса production. Проверяется отсутствие чтения секретных файлов,
обработка недоступных служб, Docker, ссылок, хешей, HTTP 200 с HTML вместо health
JSON и невозможность перезаписать существующий файл отчёта.
