# Большой аудит Voice Polisher Bot — 26 июля 2026

> Полный аудит кодовой базы + исследование провайдеров. Здесь: почему бот
> сломался, что исправлено в этой сессии, что осталось сделать, и какие есть
> бесплатные альтернативы Groq.

---

## 1. TL;DR — почему «работал только Polish (Сырой/Обычный)»

Симптом складывался из **трёх независимых поломок**, наложившихся друг на друга:

### Причина 1 (главная): Groq деприкейтнул основную модель
`llama-3.3-70b-versatile` и `llama-3.1-8b-instant` **деприкейтнуты Groq
17 июня 2026, отключение «до августа 2026»**. На `llama-3.3-70b-versatile`
работали **все** режимы (кроме coder_strict). При отключённой модели каждый
запрос делал 3 бессмысленных ретрая и падал с «Сервер временно недоступен».
Официальная замена от Groq: `openai/gpt-oss-120b` или `qwen/qwen3.6-27b`.
**✅ Исправлено:** дефолт мигрирован на `openai/gpt-oss-120b`, добавлена
фолбэк-цепочка (`LLM_MODEL_FALLBACKS`), ошибка `model_decommissioned`
распознаётся и переключает модель вместо ретраев.

### Причина 2: выбор режима не сохранялся
Кнопка режима («ПРОМПТ», «ПЕРЕВОД»…) **вообще ничего не писала в БД** — режим
сохранялся только при выборе конкретного стиля. Плюс запись стиля шла в одной
транзакции с `edit_text`: любая ошибка Telegram (старое сообщение >48ч,
повторное нажатие того же стиля) **откатывала сохранение молча**. Плюс
`update_user_settings` был слепым UPDATE: если строки юзера нет (свежая БД
после замены Supabase) — обновлялось 0 строк без ошибки. Итог: юзер жмёт
кнопки, а бот всегда сваливается в захардкоженный дефолт — а это буквально
`polish` + `polish_default`. Вот почему «работали только первые два стиля
полировки».
**✅ Исправлено:** кнопка режима персистит выбор сразу; запись настроек
коммитится до `edit_text`; перед UPDATE гарантируется существование строки.

### Причина 3: мёртвая БД = молчащий бот
Истёкшая Supabase убивала всё: бот не стартовал (`load_skills` — первый вызов,
Dockerfile ронял контейнер в restart-loop при падении миграций), проверка бана
в `AuthMiddleware` глушила каждое сообщение, готовые ответы LLM выбрасывались
из-за падения записи истории, кнопки настроек крутили вечный спиннер.
**✅ Исправлено:** полный слой устойчивости (см. раздел 3).

### Отдельно: Prompt-режим не работал никогда
`max_tokens=8000` + до 6000 символов skills-контекста + длинный системный
промпт ≈ 12–14k токенов на запрос при TPM-лимите free-tier ~6–12k → **каждый**
запрос Prompt-режима получал 429/413.
**✅ Исправлено:** `max_tokens=4000`, skills-контекст ужат до 3000 симв.

## 3. Что исправлено в этой сессии (2 коммита)

### Миграция моделей + фолбэки
- `llm_model_default`: `llama-3.3-70b-versatile` → **`openai/gpt-oss-120b`**
- `llm_model_fast`: `llama-3.1-8b-instant` → `openai/gpt-oss-20b`
- Новое: `LLM_MODEL_FALLBACKS=qwen/qwen3.6-27b,llama-3.3-70b-versatile`
- `complete()`: авто-`reasoning_effort`/`reasoning_format="hidden"` для всех
  gpt-oss (иначе пустой content — грабли CLAUDE.md №14), распознавание
  `model_decommissioned`/404 → переключение на запасную модель,
  `ModelUnavailableError` + отдельное сообщение юзеру, постоянные 4xx без ретраев.
- `transcribe()`: фолбэк `whisper-large-v3` → `whisper-large-v3-turbo`.

### Слой устойчивости к мёртвой БД (`src/storage/user_context.py`)
- Чтение/запись настроек юзера: БД → при недоступности in-memory фолбэк
  (`load_user_context` / `save_user_settings`), с авто-ресинком в БД после
  её оживления.
- Результат LLM доставляется **до** записи истории; `save_request` best-effort.
- `load_skills()` не роняет старт; Dockerfile не уходит в restart-loop при
  падении миграций/синка; auth-бан fail-open при мёртвой БД.
- Кэш транскрипции best-effort (двумя точками — чтение и запись).
- Таймауты БД: connect 10с, command 30с (зависший Supabase не вешает пул).
- Глобальный `dp.errors()`: юзер всегда получает ответ, не тишину.

### Устранённые баги поведения
- Кнопка режима персистит выбор (B3); сброс стиля при смене режима.
- Auth + rate-limit на callback_query (бан/лимиты обходились кнопками, B14).
- «Повтор» у забаненного юзера больше не запускает LLM бесплатно.
- /settings корректно показывает стили Summary/Перевод (B26).
- /lang не принимает мусорные коды (B27).
- /stats и /sync_skills не падают на Markdown-символах (B32).
- /sync_skills перезагружает in-memory индекс без рестарта (B15) и
  переживает таймаут подпроцесса.
- SkillsDB держит в памяти лёгкие строки, а не полные ORM-объекты (риск OOM
  на 512 МБ Render, B16).
- Пустой ответ модели показывается с клавиатурой (B21); split_text не создаёт
  части в 1 символ (B36).
- get_or_create_user обновляет username/first_name (B30).
- Миграция с индексами: `request_history(user_id, created_at)`,
  `transcription_cache(created_at)`, `skills_index(skill_name)` (B22).
- `.env.example` синхронизирован с реальностью: whisper **без** turbo,
  голосовые до 1 часа, `GROQ_API_KEY_SUMMARY`, новые модели (B37, B38, B9).
- TTL кэша транскриптов 1 → 7 дней (B39).

## 4. Что осталось (не блокирует, по приоритету)

1. **[после замены БД владельцем]** Прогнать `alembic upgrade head` на новой
   БД (индексы) и `/sync_skills`.
2. **Мульти-провайдерный фолбэк** (Cerebras LLM / SambaNova STT) — конфиг
   `*_base_url` + ключи, `complete()` уже почти готов к этому.
3. Экспорт `.txt` для многочастных ответов собирает только последнюю часть;
   для файлового фолбэка кнопка бесполезна (B29). Хранить полный текст в
   `_last.py` и экспортировать из него.
4. Реплай текстом на голосовое уходит в voice-хендлер, текст игнорируется
   (B19) — редкий кейс, нужен приоритет text-ветки при наличии своего текста.
5. Мёртвый хендлер `action:set_default:` и неиспользуемые
   `skills_auto_sync_on_startup`/`skills_sync_interval_hours`, `states.py`,
   `services/audio.py` (тянет pydub, ломающийся на Python 3.13) — вычистить.
6. `total_voice_seconds`, `TranscriptionCache.duration_sec/language`,
   `RequestHistory.error` объявлены, но не заполняются (B31).
7. Redis для rate-limit и стора «Повтора» — при масштабировании >1 реплики.
8. Тестами не покрыты callbacks/middlewares (частично закрыто
   `test_resilience.py`, но хендлеры кнопок — нет).
9. Запинить зависимости (lock-файл) — сейчас `>=`, воспроизводимость сборки
   не гарантирована.
10. `audit_report.txt` в корне устарел — источник правды теперь этот файл.

## 5. Чек-лист владельцу при замене БД

1. Взять новую строку подключения (Supabase session pooler, порт 5432),
   префикс заменить на `postgresql+asyncpg://`.
2. Обновить `DATABASE_URL` в Render → бот передеплоится, миграции пройдут
   автоматически (включая новые индексы).
3. Проверить `/stats` (админ) — БД живая; отправить голос в Polish и текст в
   Prompt — оба должны отвечать.
4. Если Render показывает «WARN: migrations failed» в логах — БД недоступна,
   но бот всё равно поднимется и будет работать без истории (новое поведение).
5. Ключи Groq: достаточно одного `GROQ_API_KEY_FALLBACK`; per-mode ключи
   имеют смысл только если это ключи **разных** аккаунтов Groq.
